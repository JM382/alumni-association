# 校友社交小程序 - 系统设计文档

> 基于微信小程序 + 云开发 CloudBase 的完整系统设计，用于指导后续开发。  
> 开发范围：**微信一键登录**、**校友圈（动态 + 活动报名 + 校友查找）**、**我的（个人中心 + 设置）**；预留 **会员与福利权限** 扩展。

---

## 一、开发范围与用户角色

### 1.1 开发范围

| 模块 | 说明 | 主要能力 |
|------|------|----------|
| 微信一键登录 | 用户身份与会话 | 获取 openid、创建/更新用户记录、与云数据库用户表联动 |
| 校友圈 | 动态广场 + 活动报名 + 校友查找 | 发布图文/视频动态（含话题）、点赞/评论、活动列表与报名、校友搜索与筛选、私信/加好友（需认证） |
| 我的 | 个人中心 + 设置 | 个人信息卡片、电子校友卡、卡包/积分/通讯录/我的活动/订单/捐赠/找人脉/资源/个人信息、账号/消息/隐私/帮助/关于我们 |

### 1.2 用户角色与权限（与《角色与权限实现清单》一致）

| 角色 | 标识 | 说明 | 权限要点 |
|------|------|------|----------|
| 游客 | 未登录或未注册 | 限浏览公开内容 | 仅可浏览，发动态/报名/加好友等需登录或认证 |
| 校友 | accountType=alumni，isCertified | 九校一院校友，完成注册与认证 | 发动态、报名活动、校友查找、加通讯录需 isCertified |
| 企业 | accountType=enterprise | 校友企业、合作机构 | 由管理员录入或企业注册，可参与福利、捐赠等 |
| 会员 | memberStatus=active，未过期 | 开通会员的校友 | 电子校友卡、会员专属福利（后续按 memberType 分配） |
| 管理员 | accountType=admin，roles | 一级/二级管理员 | 会员管理/企业管理/经费管理/专家管理；发布活动、审核认证、发布新闻等 |

**权限约定**（后续开通会员与福利时沿用）：

- 发动态 / 报名活动 / 发起活动：需 **isCertified**（已认证校友）。
- 电子校友卡展示/分享：需 **isCertified** 且 **memberStatus=active** 且未过期。
- 校友查找-加好友/私信：需登录且 **isCertified**。
- 活动创建、认证审核、新闻发布等：云函数内校验 **isCertified** 与 **admin**。

### 2.2 各层职责

| 层级 | 职责 |
|------|------|
| **小程序前端** | 页面渲染、用户交互、调用云函数与云存储 API、本地缓存与登录态维护 |
| **云函数** | 鉴权（openid）、业务逻辑、数据库读写、聚合与分页、权限校验 |
| **云数据库** | 用户、学校、动态、点赞、评论、通知等结构化数据持久化 |
| **云存储** | 图片/视频文件存储，返回 fileID 供数据库引用与展示 |

### 2.3 技术栈约定

- **前端**：微信小程序原生（WXML / WXSS / JS），云开发 SDK `wx.cloud`。
- **后端**：云函数（Node.js），云数据库（文档型），云存储。
- **鉴权**：云函数内通过 `cloud.getWXContext().OPENID` 识别用户，不依赖自定义 token（可选在云函数内校验登录态）。

## 三、数据库设计

### 3.0 设计原则与层次结构

- **以使用者为根**：每个「使用者」在系统中对应一个唯一标识 **user_id**（可与 users 文档的 _id 一致，或单独生成）。所有与该使用者相关的数据，要么落在该使用者的 **users 文档内部**（分组嵌套），要么落在 **其他集合** 中并以 **user_id** 明确归属。
- **users 集合的层次感**：每条 users 文档 = 一个使用者（一个「对象」）。文档内部不采用扁平字段堆砌，而是用 **分组对象** 划分层次，便于扩展权限与信息：
  - **base**：登录与身份（openid、user_id、创建/登录时间）
  - **profile**：通用资料（昵称、头像、手机、邮箱、性别、生日、城市、简介等）
  - **permission**：角色与权限（accountType、isCertified、roles、cardNo）
  - **alumni**：校友注册信息（学校、姓名、学号、年级、专业、单位等）
  - **enterprise**：企业注册信息（企业名、行业、信用代码、联系人等）
  - **member**：会员状态（memberStatus、memberType、memberExpireAt）
  - **points**：积分余额（与 point_logs 一致的冗余）
- **其他集合的归属**：订单、通讯录、积分流水、卡包、捐赠、通知设置等，均 **具体到在具体使用者下**：每条记录必带 **user_id**（或 userId），表示「该条数据属于哪个使用者」。查询时先按当前登录用户的 user_id 过滤，再在该使用者维度下做列表/分页/统计。
- **与现有实现的关系**：云函数仍通过 openid 定位用户；openid 对应 users 中唯一文档，该文档的 _id 即作为 user_id 供订单、通讯录等集合引用。若已有集合使用 userId 字段，与 user_id 含义一致，可继续沿用。

---

### 3.1 集合总览

| 集合名 | 说明 | 归属方式 |
|--------|------|----------|
| users / alumni_users | 用户信息（按 base/profile/permission/alumni/enterprise/member 分组嵌套，一个文档 = 一个使用者） | 以 _id 作为 user_id，唯一标识使用者 |
| schools | 学校/校友会信息（九校一院，管理员录入） | 全局，不按使用者划分 |
| posts | 校友圈动态（含话题标签） | authorId = user_id，归属发布者 |
| likes | 动态点赞记录 | userId = user_id |
| comments | 动态评论 | userId = user_id |
| notifications | 互动通知（点赞、评论、回复；可扩展活动/系统通知） | receiverId = user_id |
| activities | 活动（线上讲座、线下聚会、返校日、行业交流等） | creatorId = user_id |
| activity_enrollments | 活动报名记录（与「我的活动」联动） | userId = user_id |
| contacts | 通讯录/好友关系（我添加的校友、组织） | userId = user_id |
| user_cards | 卡包（校友卡、合作福利会员卡等） | userId = user_id |
| point_logs | 积分流水（余额在 users 内冗余） | userId = user_id |
| orders | 我的订单（酒店、机票、租车、快递等，具体到使用者下） | userId = user_id |
| donations | 捐赠记录与证书 | userId = user_id |
| notification_settings | 用户通知开关（活动/系统/互动） | userId = user_id，一对一 |
| member_tiers | 会员等级/权益（预留，后续开通会员与福利） | 全局配置 |
| welfare_benefits | 合作福利配置（预留） | 全局配置 |

> **说明**：若项目已存在 `alumni_users` 集合，可按本设计改为分组嵌套结构并保留 openid 唯一；云函数继续使用 `alumni_users` 亦可。订单、积分、通讯录等集合一律带 **user_id / userId**，表示「该记录属于哪个使用者」。

## 四、云函数设计

### 4.1 用户相关

**user_id 约定**：在**登录过程**中为每个用户生成并落库唯一 **user_id**（新用户创建时生成，老用户首次登录若无则用 _id 补全）。login、getUserInfo 的返回数据中均包含 **user_id**。后续所有写入 **orders、contacts、point_logs、user_cards、donations、notification_settings** 等「归属使用者」的集合时，云函数应先用 openid 查 users 取 **user_id**（或 doc.user_id \|\| doc._id），再以该值作为记录的 **userId** 字段写入，保证数据归属到具体使用者。

#### login

| 项 | 说明 |
|----|------|
| **功能** | 获取当前用户 openid；若数据库中无对应用户则**创建记录并生成唯一 user_id**，有则更新最后登录时间并返回用户信息；老用户若无 user_id 则本次登录补全。 |
| **输入** | `{ nickname?, avatarUrl? }`（可选，首次创建时写入） |
| **返回** | `{ success, user: { _id, user_id, openid, nickname, avatarUrl, ... } }`，其中 **user_id** 供前端及其他集合归属使用。 |
| **逻辑** | 1）getWXContext().OPENID；2）where({ openid }).get()；3）有则 update lastLoginTime，若无 user_id 则 update user_id = _id，并返回用户；4）无则生成 user_id 后 users.add({ openid, user_id, nickname, avatarUrl, createTime, lastLoginTime, ... }) 后返回。 |

#### getUserInfo

| 项 | 说明 |
|----|------|
| **功能** | 根据当前用户 openid 查询并返回用户资料（用于个人中心、发动态时展示）；返回数据中带 **user_id**。 |
| **输入** | 无（或空对象） |
| **返回** | `{ code, msg, data: userDoc }`，data 中包含 **user_id**（doc.user_id \|\| doc._id）。 |
| **逻辑** | openid 查 users 集合 limit(1)，将 user_id 并入 data 后返回。 |

#### updateUserProfile

| 项 | 说明 |
|----|------|
| **功能** | 更新当前用户资料：基础信息、教育背景、职业信息、隐私设置；支持校友/企业注册信息提交（认证审核前填写）。 |
| **输入** | `{ profile: { nickname?, avatarUrl?, schoolId?, schoolName?, realName?, idNoOrStudentNo?, enrollmentYear?, graduationYear?, major?, education?, phone?, email?, region?, company?, position?, bio?, ... } }`；企业账号可传 companyName、industry、creditCode、address、contactName 等。 |
| **返回** | `{ code, msg, data?: { userId } }` |
| **逻辑** | 根据 openid 找到用户 doc，update 仅更新传入的字段；若提交认证相关字段可置 isCertified=false 待审核，审核通过由管理员或认证云函数置 isCertified=true 并分配 cardNo。 |

## 七、开发建议

### 7.1 数据库索引

建议在云开发控制台为以下查询建立索引，避免全表扫描与超时：

| 集合 | 索引字段 | 说明 |
|------|----------|------|
| users / alumni_users | openid（唯一）或 base.openid（嵌套结构时） | 登录、getUserInfo |
| users | permission.isCertified、alumni.schoolId、alumni.enrollmentYear、alumni.major、alumni.region、enterprise.industry（嵌套结构时） | 校友查找 searchAlumni 组合筛选 |
| posts | status + createTime 降序 | 列表分页 |
| posts | status + tags（数组） | 话题筛选 |
| posts | authorId + createTime | 个人动态列表 |
| likes | userId + postId（联合唯一） | 判重、取消点赞 |
| likes | postId | 某动态点赞列表（若需要） |
| comments | postId + createTime | 评论列表分页 |
| notifications | receiverId + createTime 降序 | 通知列表、未读数 |
| activities | status + createTime 降序 | 活动列表分页 |
| activities | creatorId + createTime | 我发起的活动 |
| activity_enrollments | activityId + userId（联合唯一） | 报名判重 |
| activity_enrollments | userId + createTime 降序 | 我的活动列表 |
| contacts | userId + targetId（联合唯一） | 通讯录判重、列表 |
| user_cards | userId | 卡包列表 |
| point_logs | userId + createTime 降序 | 积分流水 |
| orders | userId + createTime 降序 | 我的订单 |
| donations | userId + createTime 降序 | 我的捐赠 |
| notification_settings | userId（唯一） | 通知开关查询 |

### 7.2 安全规则

- **云数据库**：建议仅云函数写库，前端不直连 DB 写；读可根据需求开放部分集合的读权限（如 schools 只读）。
- **云函数**：① 所有写操作通过 `getWXContext().OPENID` 校验身份；② **按角色与权限校验**：发动态/报名/加好友等需 **isCertified**，创建活动/审核等需 **admin**，电子校友卡展示需会员有效；③ 资源归属校验（如 deletePost 仅作者可删）。
- **隐私与脱敏**：校友查找 searchAlumni 仅返回用户设置的可见信息；手机号、邮箱等按「隐私设置」决定是否对他人展示。
- **云存储**：上传目录按业务划分（如 `postImages/`、`avatars/`、`certificates/`），可在云存储控制台设置仅登录用户可写、可读。

### 7.3 分页方案

- **推荐游标分页**：以 `createTime` 或 `_id` 作为游标，请求带上 `lastCreateTime` 或 `lastId`，云函数用 `where().orderBy().limit().startAfter()` 实现，避免 skip 过大导致性能差。
- **页号分页**：若必须用 pageNum，建议 limit 不超过 20，并配合索引使用。

### 7.4 图片存储方案

- 发布动态：小程序端 `wx.chooseMedia` 选图 → `wx.cloud.uploadFile` 上传至云存储（如 `postImages/{openid}_{timestamp}_{i}.jpg`），将返回的 fileID 数组传给 `createPost`。
- 列表/详情展示：数据库存 fileID，前端用 `wx.cloud.getTempFileURL` 批量换取临时链接后展示，或直接使用云存储 CDN 链接（若已配置）。
- 头像：同理会用云存储 fileID 或 HTTPS URL 存于 users.avatarUrl。

### 7.5 性能与体验建议

- 动态列表做虚拟列表或分页加载，避免一次拉取过多条。
- 点赞数、评论数用冗余字段，避免列表页对 likes/comments 做聚合查询。
- 通知未读数可用云函数聚合 count，或登录时拉取一次并缓存在本地，进入通知页再刷新。
- 云函数内做好 try/catch，统一返回 { code, msg, data }，前端根据 code 做提示与跳转。
